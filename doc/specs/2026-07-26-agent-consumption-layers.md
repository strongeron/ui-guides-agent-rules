# Agent Consumption Layers

**Date:** 2026-07-26
**Status:** Draft — awaiting approval before `ce-plan` / implementation
**Relates to:** `2026-07-26-real-routes-and-prerender.md` (independent; see Sequencing)

## Problem

New requirement: the corpus should be something an agent working in *another*
repo can check, validate against, and apply — a reference layer, not just a site.
Today it cannot, for two measured reasons.

**1. The only machine payload is all-or-nothing, and "all" does not fit.**

| Payload | Tokens | Verdict |
|---|---|---|
| `llms-full.txt` — everything | **166,000** | unusable as context |
| one category (`interactions`) | 18,900 | usable |
| one category (`forms`) | 4,000 | cheap |
| all 191 MUST rules, rule text only | 9,500 | cheap |
| a single rule | 93 | free |

The README's current answer is `curl | awk` to slice a category out of the full
file — honest, but it makes the agent download 166k tokens' worth to keep 4k, and
there is no slice smaller than a category.

**2. The examples — the whole point of the project — are invisible to agents.**

809 example components, 3.3 MB, and not one byte is reachable from any machine
endpoint. `llms-full.txt` carries the rule and the prose but not the good/bad code.
An agent asked to *apply* a rule gets the assertion without the demonstration,
which is exactly the part that disambiguates it.

## Constraints

- **Static hosting.** Everything must be a file generated at build time. No
  server, no query strings that need computing.
- **One source of truth.** `src/data/principles/**` plus the example components
  already generate `llms.txt`/`llms-full.txt`. New endpoints come from the same
  pass or they drift.
- **Skill sprawl is a real cost.** `web-design-guidelines` (1.3 KB) and
  `ui-skills` (3.4 KB) already exist and already claim this job. Per the
  >60%-overlap rule, a new `ui-guides` skill would be a near-duplicate.
- **Portability.** Consumption must work from Claude Code, Codex, and Cursor,
  which rules out anything requiring a bespoke runtime in each project.

## Options

### A. MCP server (`search_rules`, `get_rule`, `validate`)

- **Pro:** richest interface; real search.
- **Con:** needs a running server and per-project configuration; the corpus is
  static, so this is a server built to serve files that could just be files. Does
  not work from a bare `curl`. Highest ceiling, worst friction-to-value.

### B. Sliceable static endpoints + progressive disclosure ✅

Generate a small index and many small payloads; let the agent fetch the slice it
needs. This is the same progressive-disclosure shape Agent Skills use, applied to
data instead of instructions.

- **Pro:** free to host, works from `curl`, `WebFetch`, any agent, any editor.
  Cache-friendly. Falls out of the existing generator.
- **Con:** no server-side search — the agent filters the index itself. Acceptable:
  the index is ~12k tokens and filtering it is what agents are good at.

### C. npm package / CLI (`npx ui-guides check`)

- **Pro:** enables real static checks and CI use.
- **Con:** only helps JS projects with an install step, and most rules are not
  statically checkable. Valuable *later*, on top of B, not instead of it.

## Chosen direction

**B**, generated by the existing build, published as static files:

| Endpoint | Approx. tokens | What it is for |
|---|---|---|
| `/llms.txt` | 1,000 | already shipped — names the categories |
| `/principles/index.json` | 12,000 | id, title, priority, category, tags, url — **pick, then fetch** |
| `/principles/must.md` | 9,500 | the 191 MUST rules — a cheap pre-commit gate |
| `/categories/<category>.md` | 4,000–19,000 | one category, whole |
| `/principles/<id>.md` | ~1,000 | one rule **+ its good and bad example source** |
| `/principles/<id>.json` | ~1,000 | same, structured |
| `/llms-full.txt` | 166,000 | unchanged; rarely the right fetch |

The per-rule endpoint is the substantive new thing: it is the first time the 3.3 MB
of example components become reachable, and at ~1k tokens a rule an agent can
afford to pull several while working.

**Distribution: extend `web-design-guidelines`, do not add a skill.** Its stated
job — "review UI code for Web Interface Guidelines compliance" — is already this
job; it is a 1.3 KB stub pointed at one upstream source covering 118 of 404 rules.
Repointing it at the full corpus with a fetch ladder (index → category → rule)
turns a stub into the real thing without adding a 15th overlapping skill.
`ui-skills` (ibelick, 50 rules already in the corpus) should be folded in or left
alone deliberately — not silently duplicated.

## Sequencing — this lands *before* routes

The new requirement makes the machine layer more urgent than the SEO layer, and
the two are independent. `/principles/<id>.md` is a generator change that needs no
routing; `/principles/<id>` as an HTML page is the prerender work. Doing the data
layer first means agents can use the corpus while the SSG work is still in review,
and the URL namespace already agreed (`/principles/<id>`) keeps them consistent.

## Scope

- Generator emits the index, per-category, per-rule `.md` and `.json`, and `must.md`.
- Example component source is extracted into the per-rule payloads.
- `web-design-guidelines` skill rewritten around the fetch ladder.
- README's `curl | awk` section replaced with the real endpoints.
- Guard, matching the existing llms.txt assertion: fail the build if any published
  principle is missing a payload, or if a payload loses its example code.

## Non-goals

- MCP server (option A) and npm CLI (option C). Both are reasonable later; neither
  is the cheapest path to the stated need.
- Static rule-checking / lint rules. Wants a `detectability` field on the data
  model first — see Open questions.
- Changing the principle data model, the site UI, or the SSG plan.

## Open questions

1. **Does a rule payload carry both examples in full, or the bad one trimmed?**
   Both is ~1k tokens and shows the contrast the project exists to show. Bad-only-
   as-a-diff would halve it. Recommend both, in full.
2. **Should rules gain a `detectability` field** (`static` | `visual` | `judgment`)?
   It is what would later let a skill run cheap grep checks before spending a model
   call, and it is a data-model change best made once. Recommend yes, as a
   follow-up rather than blocking this.
3. **`ui-skills`: fold in or leave?** Its 50 rules are already in the corpus. Two
   skills asserting overlapping UI constraints is the sprawl this spec is trying
   to avoid.
